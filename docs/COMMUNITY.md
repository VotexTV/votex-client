# Votex Community

Later checkpoint,25October2026: [COMMUNITY-CONTRACT-20261025.md](COMMUNITY-CONTRACT-20261025.md) records deployed Worker validation fixes, real-SQL local ownership/visibility checks, actual launcher-builder payloads and complete PNG fixtures. Sites version11 is live; real authenticated-account mutation acceptance remains open. Historical statements below about no backend change apply to their earlier24October checkpoint.

Community contributions are created in the Windows client. New contributions default to public after the creator confirms the final action. The creator can keep a contribution private on the device, publish it to discovery, or make it unlisted and share it by a private link. Cape images use the same choices. Changing an unlisted contribution to private or public revokes its old link; choosing unlisted again creates a new one.

The public feed displays the Minecraft player name and the submitted model, animation, or cape. To verify ownership and protect each creator's entries, the launcher refreshes the selected account and sends the short-lived Minecraft access token to the Votex community endpoint only for an explicit publish, visibility change, deletion, or report. The service forwards the token to Minecraft's official profile endpoint and does not store or log it. The Votex database stores the Minecraft profile UUID privately for ownership checks. A report stores the item's identifier, the reporter's private profile UUID, a reason, optional details, and its timestamp.

Private and unlisted items do not appear in public discovery. An unlisted link can be pasted into the Cosmetics or Animations page to import the item. Deleting an item removes its database row and prevents new downloads. Reports remain as moderation records. Copies already imported by other players remain on their devices. Community content does not automatically appear on other players' Minecraft screens.

The service accepts bounded geometry and keyframe data only. It never executes model or animation scripts. Existing community tables are migrated additively: published entries remain public and hidden entries become private. The Minecraft API approval for Votex is pending; until Microsoft/Mojang approves the application, community actions that require a fresh Minecraft profile token may be unavailable.

## Read-only acceptance checkpoint, 2026-10-24

The current public cape, cosmetic and emote listing endpoints each returned HTTP200 with a valid empty list and null nextOffset. The owner-only `/items/mine` endpoint rejected the anonymous request with HTTP401. Exact metadata is retained in `work/ingame-goal/community-readonly-20261024.json`; no account credentials were accessed and no external data was written. An empty public feed cannot prove private-item filtering, ownership enforcement across two authenticated users or actual publication/unpublication/republication. Those remain distinct authenticated acceptance checks.

The launcher source supports public/unlisted/private choices and changing an existing remote item's visibility by its stable ID; a later publication of a local private item uses the creation path. New model/emote/cape share flows select public by default. Failed authenticated mutations do not set the local published flag to success. This source audit does not replace executing those mutations against the service. No offline identity was substituted for the required Minecraft profile token, and neither the website nor its backend was modified or redeployed.

The audit found a local-Cape exception to that intended behavior: selecting public on a cape without a remote ID optimistically set `capePublished=true` before the upload had succeeded. This is corrected by routing cape visibility through a single committed-result service. The page applies its saved state only after the action resolves; rejection leaves the previous state intact. A private local cape stays local, an empty cape is never marked published, and changing visibility on a remote cape retains its ID. Four IPC-mocked workflow tests cover local-private→public, delayed/failing upload, stable-ID private/unlisted/public cycles and empty image handling. These tests intentionally make no authenticated-server claim. All97 frontend tests across22 files, TypeScript and the Vite production build pass after this fix. The build retains the existing large-chunk advisory. No updated EXE was packaged or opened for this later frontend-only change.
